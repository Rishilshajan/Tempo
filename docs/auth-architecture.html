2Token model — yes, it is JWT-based

Supabase Auth issues two credentials on a successful sign-in:

TokenWhat it isLifetimeRole
Access tokenSigned JWT — sub (user UUID), email, role, exp, aud~1 hourProves identity on every request
Refresh tokenOpaque, single-use, rotating stringDays (configurable)Mints a fresh access token when the old one expires

The access token is a genuine JWT (header.payload.signature) signed by the project's key. Because the signature is verifiable, the server trusts the userId inside it without a database lookup. We never issue our own JWT, never hash passwords ourselves, and never maintain a session table — GoTrue does all of that.

Rotation: each use of the refresh token invalidates it and issues a new one. A stolen refresh token is therefore detectable (reuse → the whole family is revoked).

3Where the tokens live — cookies, not localStorage

This is the decision that makes @supabase/ssr necessary. Tokens are written to HttpOnly, Secure, SameSite=Lax cookies (chunked across several cookies when large), not to browser localStorage.

  • HttpOnly → client-side JS cannot read them → XSS cannot exfiltrate the session.
  • Secure → only sent over HTTPS.
  • Cookies ride along with every request automatically, so Server Components, Server Actions and Route Handlers all see the session with zero manual header passing.

         • Drizzle query filtered by userId   ← app-level data isolation

LOGOUT  (Server Action)
  supabase.auth.signOut()  → cookies cleared  → redirect('/login')

5Two-tier enforcement: Proxy (optimistic) vs DAL (secure)

Next.js 16 guidance (and this repo's pinned docs) is explicit: the proxy is a convenience gate, not the security boundary. Authorization must happen close to the data.

OPTIMISTIC proxy.ts

  • Reads the session cookie only — no DB calls (runs on every prefetch).
  • Refreshes expiring tokens and rewrites cookies.
  • Redirects unauthenticated users away from protected routes and authenticated users away from auth pages.
  • Renamed from middleware.ts; exports proxy + config.matcher.

SECURE Data Access Layer

  • requireUser() calls supabase.auth.getUser() which verifies the JWT.
  • Wrapped in React cache() → one verification per render pass.
  • Called inside every protected query and every Server Action (treat actions as public endpoints).
  • Returns the userId that scopes all Drizzle queries.
getUser() vs getSession(): getSession() merely decodes the cookie — fast but spoofable on the server. The DAL always uses getUser()/getClaims(), which validate the signature. Never gate data on getSession() alone.

export const passwordSchema = z
  .string()
  .min(8, "At least 8 characters")
  .regex(/[A-Z]/, "One uppercase letter")
  .regex(/[a-z]/, "One lowercase letter")
  .regex(/[0-9]/, "One number")
  .regex(/[^A-Za-z0-9]/, "One special character");

export const credentialsSchema = z.object({
  email: z.email("Enter a valid email"),
  password: passwordSchema,
});

8Error handling — toasts

Auth Server Actions return the codebase's existing discriminated union ActionResult<T> = {ok:true,data} | {ok:false,error}. The client form fires a Sonner toast.error(result.error) on failure and toast.success(...) on success. Validation failures short-circuit before any Supabase call. Supabase errors (wrong password, unconfirmed email, duplicate account) are mapped to friendly copy.

10Data model & per-user scoping

The current schema is single-user (no user_id anywhere). Phase 1 adds a userId uuid (= Supabase auth.users.id) to every ownership root and threads it through every query and action.

TableChange
domains, tasks, push_subscriptions, warning_rulesAdd user_id NOT NULL; indexes lead with user_id
app_settingsAdd user_id + UNIQUE → one settings row per user (was one global row)
task_milestones, dependenciesDenormalize user_id onto both — every scoped query becomes a trivial eq(userId) and cross-user edges are impossible
notification_logAdd user_id; UNIQUE on (user_id, slot) so send-once is per user
Why app-level, not RLS (yet): Drizzle connects with the service connection string, which bypasses Postgres Row-Level Security. Scoping in the DAL is explicit and testable now; RLS is added later as defense-in-depth once the user JWT is routed to the DB layer.

11Migration & backfill strategy

  1. Migration A — add user_id as nullable to every table (non-destructive; app keeps running).
  2. Sign up — create the first real account; note its UUID.
  3. Backfill — one-time UPDATE … SET user_id = <uuid> WHERE user_id IS NULL across all tables, claiming existing single-user data.
  4. Migration B — flip user_id to NOT NULL and swap in the user-scoped indexes.
Generated, not auto-applied. Migrations are produced with drizzle-kit generate and reviewed before db:migrate runs against Supabase.

12Security considerations

  • XSS → HttpOnly cookies mean injected JS can't read the session.
  • CSRF → SameSite=Lax cookies + Server Actions' same-origin POST model.
  • Server trust → authorization decisions only ever use verified getUser(), never getSession().
  • Key hygiene → only the anon key is public (NEXT_PUBLIC_); the service-role key is never shipped to the client.
  • Least data → DAL returns only the fields a caller needs (DTO discipline); sensitive JWT fields never cross to the client.
  • Action hardening → every mutating Server Action calls requireUser() first and scopes writes by userId.
